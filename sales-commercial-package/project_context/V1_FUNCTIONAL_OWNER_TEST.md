# V1 functional owner test

Дата: 2026-07-08.

Статус: тест-опрос для утверждения функций всех страниц v1 перед дизайн-полировкой, backend/admin и авторизацией. Код, CSS, JS, HTML и `js/app.js` не менялись.

## 1. Почему сначала тест функций

Перед админкой и backend-панелью нужно утвердить, чем именно управляет администратор.

Правильный порядок:

1. Утвердить функции страниц.
2. Закрыть логику v1.
3. Доработать visual/mobile/dark.
4. Зафиксировать data model.
5. Потом проектировать backend/admin/auth.

Если сделать админку раньше, она начнет управлять спорной или недоделанной логикой.

## 2. Как проходить тест

По каждой зоне владелец отвечает коротко:

```text
да
нет
v2
позже
нужно обсудить
```

После ответов Architect / Main фиксирует:

- что входит в v1;
- что уходит в v2;
- что является backend/admin requirement;
- что нужно доделать визуально;
- что не трогать.

## 3. Главные зоны v1

### A. Главная / общая витрина

1. Главная должна сразу быть рабочим каталогом, без лендинга?
2. Верхняя навигация: `Застр.`, `Новые`, `Готовые`, `Бизнес` - оставляем как основные v1 входы?
3. Stories остаются быстрым просмотром категорий и контента?
4. Темная/светлая тема обязательна в v1?
5. Search нужен в v1 как рабочая функция или пока визуальный элемент?
6. CTA формы заявки не делаем сейчас?

### B. Застройщики

1. В v1 застройщик - это карточка компании с лайками, подписками, рецензиями и объектами?
2. Статусные точки `строится/отстроено` оставляем как легенду у списка?
3. Профиль компании/застройщика должен открываться как большая страница?
4. В карточке нужны: название, адрес/районы, счетчики, профиль компании, объекты?
5. Рейтинг строим из лайков/подписок/рецензий, без платного влияния?
6. Управление данными застройщика позже через админку?

### C. Новостройки

1. В v1 каталог новостроек должен быть полностью рабочим: фильтры, карточки, виды, счетчики?
2. Фильтры v1: район, год сдачи, семья, выгода, комфорт, инвестиции?
3. Выбранные фильтры показывать после счетчика карточек?
4. Карточка ЖК открывает большую страницу объекта?
5. Лайк/подписка/рецензия работают как local v1 до backend?
6. Map/list/grid остаются v1 режимами?

### D. Готовые ЖК

1. Готовые ЖК отделены от новостроек как отдельный каталог?
2. Логика карточек такая же, как у новостроек?
3. Фильтры похожи на новостройки, но с фокусом на готовность/район/комфорт?
4. Большая страница ЖК одинаковая для готовых и строящихся?
5. Готовые ЖК должны поддерживать рецензии жителей сильнее, чем новостройки?

### E. Для бизнеса

1. Бизнес-раздел входит в v1 как отдельный каталог?
2. Фильтры бизнеса: тип сделки, район, тип помещения, площадь, бюджет?
3. Карточки бизнеса отличаются от ЖК и имеют свою структуру?
4. Виды grid/list/map обязательны?
5. Пустые состояния и reset фильтров обязательны?
6. Данные бизнеса потом должны редактироваться через админку?

### F. Страница объекта / ЖК

1. Большая страница объекта обязательна в v1?
2. Нужно оставить tabs/разделы: обзор, лента, рецензии, документы/детали?
3. Кнопка `Назад` должна возвращать в исходный каталог?
4. `Все рецензии` открывает полный список/модалку?
5. `Почему советуют` - future после backend/auth, не текущий v1 UI?
6. Документы/планировки/галерея нужны как future admin-managed data?

### G. Страница застройщика / компании

1. Большая страница застройщика обязательна в v1?
2. Должны быть объекты компании, рецензии, подписчики, публикации/stories?
3. Кнопка перехода в кабинет компании нужна только для v1 prototype?
4. Официальные материалы компании должны быть отдельно маркированы?
5. Редактирование страницы компании потом через кабинет/админку?

### H. Профиль пользователя

1. Профиль пользователя входит в v1 как витрина social layer?
2. В v1 показываем лайки, избранное, подписки, рецензии, ленту?
3. Друзья/чаты в v1: визуальный future-state или рабочая функция?
4. Ролевые профили не добавляем в текущий v1 UI?
5. CTA `Стать автором или специалистом` держим только как future-state после backend/auth?
6. Privacy полностью через backend/auth позже?

### I. Кабинет компании

1. Кабинет компании входит в v1 как prototype route?
2. В кабинете нужны: статистика, объекты, документы, публикации, stories, обращения, тариф?
3. Реальные действия кабинета не работают без backend/auth?
4. Тарифы компании остаются B2B, отдельно от тарифа физлица?
5. Представитель компании - публичная роль физлица + отдельное право доступа?
6. Админка должна уметь управлять компаниями и доступами позже?

### J. Тарифы

1. Страница тарифов размещения компаний входит в v1?
2. Тарифы физлица не показываем как реальную оплату в текущем v1 UI?
3. `Профиль автора 990 ₽/мес` держим как future hypothesis?
4. Оплата/подписки/лимиты - только после backend/auth?
5. Админка должна управлять тарифами позже?

### K. Stories

1. Stories в v1 остаются platform/company showcase?
2. Обычный пользователь не ведет stories/news?
3. Role stories только future после backend/auth/v2?
4. Текущее scroll-правило stories оставляем в планах?
5. Stories должны иметь source labels в будущей модели?
6. Управление stories потом через админку?

### L. Auth / backend / admin

1. Авторизация нужна после функционального закрытия v1?
2. Backend/admin делать после аудита страниц и data model?
3. Админка должна управлять всеми данными страниц?
4. Роли админки: admin, moderator, company manager, editor?
5. Все mock/localStorage данные должны получить migration plan?
6. Backend server подключать только после утверждения API/data contract?

## 4. Рекомендуемый порядок прохождения

1. Architect / Main готовит owner answers по этому тесту.
2. Владелец утверждает или правит.
3. Профильные чаты получают свои страницы и сверяют текущий сайт с approved function list.
4. Architect / Main собирает `V1_FUNCTIONAL_AUDIT_INTAKE.md`.
5. После этого стартует дизайн-доработка страниц.
6. Только потом backend/admin/auth implementation planning.

## 5. Что будет результатом

После прохождения теста появятся:

- `V1_FUNCTIONAL_DECISIONS.md`;
- `V1_PAGE_COMPLETION_MATRIX.md`;
- задачи чатам на functional gaps;
- отдельный admin/backend requirements pack.
