# Kliper.City: паспорт будущей страницы "Кабинет компании"

Статус на 2026-07-07: **реализован и принят v1 UI-прототип без backend/auth**.

Финальная приемка: `CAB_005_COMPANY_CABINET_V1_ACCEPTANCE.md`.

## 1. Назначение

`Кабинет компании` должен стать рабочей страницей/разделом для застройщика или компании, где она управляет своим присутствием в Kliper.City:

- публикации;
- stories;
- карточки объектов;
- подписчики;
- рецензии;
- входящие обращения;
- предложения подписчикам;
- место в рейтинге категории;
- базовая статистика.

## 2. Фактическое состояние сейчас

На странице застройщика есть текстовый блок:

```text
ДЛЯ БИЗНЕСА

Кабинет компании

Публикации, stories, подписчики, рецензии и место в рейтинге категории.
```

Реализовано:

- отдельный hash-route `#company-cabinet=developerId`, пример `#company-cabinet=brusnika`;
- отдельная кнопка `Открыть кабинет` в блоке `Для бизнеса / Кабинет компании` на публичной странице застройщика;
- отдельный overlay-экран кабинета без изменения `js/app.js`;
- возврат в публичную страницу того же застройщика через `#card=Название`;
- mock/local данные кабинета в отдельном namespace;
- desktop/mobile layout, dark-theme стили, блоки статистики, объектов, тарифа, документов, публикаций, stories, подписчиков, рецензий, обращений и предложений;
- сигналы внимания в hero: документы к проверке, обращения в работе, публикации в подготовке;
- прогресс готовности профиля в блоке `Документы и профиль`;
- v1-сообщение для будущих действий вместо молчащих disabled-кнопок.

Пока не реализовано:

- формы входа;
- backend;
- сохранения данных кабинета;
- реальные роли `company admin` / `company_owner`;
- реальные отправки, CRM, загрузка документов, ответы на рецензии;
- реальная оплата и смена тарифа.

## 3. Route

Закрепленный v1 route:

```text
#company-cabinet=developerId
```

Пример:

```text
#company-cabinet=brusnika
```

Запрещенный вариант для текущей версии: смешивать кабинет с публичной карточкой через `#card=...&mode=cabinet`.

## 4. Основные блоки будущей страницы

### Header кабинета

Показывает:

- название компании;
- статус профиля;
- кнопка назад к публичной странице;
- переключатель предпросмотра "как видит пользователь";
- CTA "Опубликовать".

### Статистика

Показывает:

- просмотры карточки;
- лайки;
- подписчики;
- рецензии;
- диалоги;
- переходы на объекты;
- место в рейтинге.

Статус: v1 mock/local. Реальная аналитика относится к backend/auth этапу.

### Тариф и лимиты

Показывает:

- текущий тариф;
- цену;
- лимит карточек;
- сколько карточек использовано;
- ссылку `Изменить тариф`.

Route страницы тарифов:

```text
#business-pricing
#business-pricing=developerSlug
```

Статус: v1 visual/mock. Реальная оплата относится к backend/billing этапу.

### Готовность профиля

Показывает состояние основных частей кабинета:

- реквизиты и подтверждение;
- связанные объекты;
- контент для ленты;
- stories компании;
- очередь обращений.

Статус: v1 local/computed. Реальная проверка документов относится к backend/auth этапу.

### Публикации

Компания может видеть список публикаций:

- новости;
- ход строительства;
- акции;
- сообщения подписчикам.

В v1 можно сделать визуальную заготовку без отправки.

### Stories

Управление stories:

- добавить story;
- заменить обложку;
- задать категорию;
- посмотреть предпросмотр.

В v1 реализовано визуально.

### Объекты

Список объектов компании:

- новостройки;
- готовые ЖК;
- бизнес-помещения, если есть.

Данные берутся из `js/data/buildings.js`, `js/data/developers.js` и отдельного mock-файла `js/data/company-cabinet.js`.

### Подписчики

Показывает пользователей, которые подписались на компанию/объекты.

Сейчас подписки локальные (`localStorage`), реального backend нет.

### Рецензии

Показывает отзывы и рецензии:

- новые;
- советуют;
- требуют ответа;
- скрытые/спорные.

В v1 только визуально или локально.

### Диалоги и заявки

Будущий блок:

- входящие сообщения;
- заявки на подбор;
- вопросы по объектам;
- быстрый ответ.

Backend не найден.

### Предложения подписчикам

Будущая функция:

- персональное предложение;
- акция;
- ранний доступ;
- приглашение на просмотр;
- рассылка по подписчикам.

## 6. Связи

Кабинет должен быть связан с:

- публичной страницей застройщика;
- карточками ЖК;
- stories;
- подписчиками;
- рецензиями;
- заявками;
- рейтингом.

Важно: кабинет не должен ломать публичную страницу компании.

## 7. Что нельзя ломать

- публичную страницу застройщика;
- карточки застройщиков;
- `#card=Название`;
- подписки пользователя;
- рецензии пользователя;
- stories;
- фильтры каталога;
- профиль пользователя `Мария`.

## 8. Риски

1. Кабинет компании легко смешать с публичной страницей застройщика.
2. Без backend это будет только визуальный прототип.
3. Если добавить route через `#card`, можно сломать page restore.
4. Если использовать те же localStorage-ключи, что у пользователя, можно смешать роли пользователя и компании.
5. Нельзя добавлять CRM-функции в v1 без решения владельца.

## 9. Вопросы владельцу

1. Это отдельная страница, drawer или модалка?
2. Кто пользователь кабинета: застройщик, менеджер, админ Kliper?
3. Какие функции должны быть рабочими первыми: публикации, stories, рецензии, заявки или статистика?
4. Нужно ли показывать кабинет обычному пользователю как CTA "Для бизнеса"?
5. Должен ли кабинет быть одинаковым для застройщика и бизнес-помещения?
6. На каком backend/auth-этапе подключаем вход в кабинет?

## 10. Рекомендуемый первый этап

Решение владельца: кабинет входит в v1.

Первый безопасный шаг - сделать **UI-прототип кабинета без backend**, а полноценный вход и данные подключить на финальном backend/auth-этапе v1:

- открыть из блока `Кабинет компании`;
- показать dashboard;
- показать публикации/stories/рецензии/подписчиков;
- все действия пометить как визуальные;
- будущие действия должны показывать понятное v1-сообщение, а не молчать;
- не менять публичную страницу застройщика;
- не трогать `js/app.js`, если можно сделать отдельным модулем.
