# Kliper.City: паспорт будущей страницы "Кабинет компании"

Статус на 2026-07-06: **есть визуально как блок на странице застройщика, отдельная рабочая страница не найдена**.

## 1. Назначение

`Кабинет компании` должен стать рабочей страницей/разделом для застройщика или компании, где она управляет своим присутствием в Kliper.City:

- публикации;
- stories;
- карточки объектов;
- подписчики;
- рецензии;
- входящие обращения;
- предложения подписчикам;
- место в рейтинге категории;
- базовая статистика.

## 2. Фактическое состояние сейчас

На странице застройщика есть текстовый блок:

```text
ДЛЯ БИЗНЕСА

Кабинет компании

Публикации, stories, подписчики, рецензии и место в рейтинге категории.
```

Но не найдено:

- отдельного route;
- отдельной кнопки входа в кабинет;
- модального окна кабинета;
- формы входа;
- backend;
- сохранения данных кабинета;
- отдельных данных компании для управления;
- роли `company admin`.

## 3. Будущий route

Варианты для решения владельца:

| Вариант | Пример | Плюсы | Минусы |
|---|---|---|---|
| SPA state | state `companyCabinet` | сохраняет текущую архитектуру | нужно трогать app/router |
| Hash route | `#company-cabinet=Брусника` | легко восстановить ссылку | может усложнить page-restore |
| Отдельный HTML | `company-cabinet.html` | изолированно | выбивается из текущего SPA |
| Модалка/Drawer | кнопка на странице застройщика | быстро для v1 | не полноценный кабинет |

Рекомендация для v1: начать с **drawer/modal-прототипа** или отдельного SPA-state без backend, но только после решения владельца.

## 4. Основные блоки будущей страницы

### Header кабинета

Показывает:

- название компании;
- статус профиля;
- кнопка назад к публичной странице;
- переключатель предпросмотра "как видит пользователь";
- CTA "Опубликовать".

### Статистика

Показывает:

- просмотры карточки;
- лайки;
- подписчики;
- рецензии;
- диалоги;
- переходы на объекты;
- место в рейтинге.

Статус: будущая функция. В v1 может быть mock/local.

### Публикации

Компания может видеть список публикаций:

- новости;
- ход строительства;
- акции;
- сообщения подписчикам.

В v1 можно сделать визуальную заготовку без отправки.

### Stories

Управление stories:

- добавить story;
- заменить обложку;
- задать категорию;
- посмотреть предпросмотр.

В v1 возможно только визуально.

### Объекты

Список объектов компании:

- новостройки;
- готовые ЖК;
- бизнес-помещения, если есть.

Данные брать из `js/data/buildings.js`, `js/data/developers.js`, `js/data/business-spaces.js`.

### Подписчики

Показывает пользователей, которые подписались на компанию/объекты.

Сейчас подписки локальные (`localStorage`), реального backend нет.

### Рецензии

Показывает отзывы и рецензии:

- новые;
- советуют;
- требуют ответа;
- скрытые/спорные.

В v1 только визуально или локально.

### Диалоги и заявки

Будущий блок:

- входящие сообщения;
- заявки на подбор;
- вопросы по объектам;
- быстрый ответ.

Backend не найден.

### Предложения подписчикам

Будущая функция:

- персональное предложение;
- акция;
- ранний доступ;
- приглашение на просмотр;
- рассылка по подписчикам.

Минимальная структура:

```js

  role: 'owner' | 'manager' | 'editor',
  stats: {
    views: number,
```

Для v1 данные можно держать в отдельном файле:

```text

```

```text
js/pages/company-cabinet/company-cabinet-page.js
css/company-cabinet.css
```

## 6. Связи

Кабинет должен быть связан с:

- публичной страницей застройщика;
- карточками ЖК;
- stories;
- подписчиками;
- рецензиями;
- заявками;
- рейтингом.

Важно: кабинет не должен ломать публичную страницу компании.

## 7. Что нельзя ломать

- публичную страницу застройщика;
- карточки застройщиков;
- `#card=Название`;
- подписки пользователя;
- рецензии пользователя;
- stories;
- фильтры каталога;
- профиль пользователя `Мария`.

## 8. Риски

1. Кабинет компании легко смешать с публичной страницей застройщика.
2. Без backend это будет только визуальный прототип.
3. Если добавить route через `#card`, можно сломать page restore.
4. Если использовать те же localStorage-ключи, что у пользователя, можно смешать роли пользователя и компании.
5. Нельзя добавлять CRM-функции в v1 без решения владельца.

## 9. Вопросы владельцу

1. Это отдельная страница, drawer или модалка?
2. Кто пользователь кабинета: застройщик, менеджер, админ Kliper?
3. Какие функции должны быть рабочими первыми: публикации, stories, рецензии, заявки или статистика?
4. Нужно ли показывать кабинет обычному пользователю как CTA "Для бизнеса"?
5. Должен ли кабинет быть одинаковым для застройщика и бизнес-помещения?
6. На каком backend/auth-этапе подключаем вход в кабинет?

## 10. Рекомендуемый первый этап

Решение владельца: кабинет входит в v1.

Первый безопасный шаг - сделать **UI-прототип кабинета без backend**, а полноценный вход и данные подключить на финальном backend/auth-этапе v1:

- открыть из блока `Кабинет компании`;
- показать dashboard;
- показать публикации/stories/рецензии/подписчиков;
- все действия пометить как визуальные;
- не менять публичную страницу застройщика;
- не трогать `js/app.js`, если можно сделать отдельным модулем.
