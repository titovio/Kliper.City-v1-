## ROLE-PRO-001: future-state CTA профессионального профиля

Зона:
Profile Social.

Ответственный чат:
Profile Social.

Цель:
Спроектировать, где и как в профиле пользователя может появиться future-state CTA `Создать профессиональный профиль` / `Стать автором или специалистом`.

Что сейчас не так:
Профиль пользователя описывает личное избранное, подписки и рецензии, но пока не объясняет будущий переход к ролевому профилю.

Можно менять:

- только документацию и продуктовый сценарий;
- future-state copy;
- wireframe-описание без кода.

Нельзя менять:

- код профиля;
- `js/behavior/user-page-finalizer.js`;
- `css/ui-ux-pro-max.css`;
- `js/app.js`;
- реальные кнопки сайта без отдельного брифа.

Файлы-кандидаты:

- `docs/ROLE_PROFILES_SCOPE.md`;
- `docs/ROLE_PROFILES_OWNER_BRIEF.md`;
- будущий отдельный отчет Profile Social.

Проверить после:

- обычный пользователь не выглядит обязанным покупать тариф;
- обычный пользователь не получает новости/stories;
- цена и возможности тарифа видны до создания;
- личный профиль не смешивается с кабинетом компании.

Ожидаемый результат:
Короткое ТЗ или UX-сценарий: где CTA находится, какие роли предлагает, что показывает до оплаты, какие решения владельца нужны.

Что считается ошибкой:
CTA выглядит как уже работающая оплата или обещает backend/auth/payment до реализации.

Нужен ли владелец:
да, подтвердить название CTA и список стартовых ролей.

## ROLE-PRO-002: теги любимого для обычного пользователя

Зона:
Profile Social + Catalog Core.

Ответственный чат:
Profile Social с review от Catalog Core.

Цель:
Спроектировать модель, где обычный пользователь после лайка/сохранения относит место к тегу любимого.

Что сейчас не так:
Сохранение и лайки есть как v1-сценарий, но нет продуктового слоя `почему пользователь сохранил`.

Можно менять:

- только документацию и сценарии;
- список стартовых тегов;
- правила приватности тегов;
- будущий handoff для backend/auth.

Нельзя менять:

- карточки;
- localStorage keys;
- UI лайков;
- профильный JS/CSS;
- `js/app.js`.

Файлы-кандидаты:

- `docs/ROLE_PROFILES_SCOPE.md`;
- `docs/SOCIAL_FEATURES_SCOPE.md`;
- будущий отчет Profile Social / Catalog Core.

Проверить после:

- пользователь не становится автором новостей;
- теги работают как сигнал, а не как публикация;
- приватные теги и публичные агрегаты разделены;
- друзья могут видеть больше только по настройкам.

Ожидаемый результат:
Сценарий `лайк -> выбрать тег`, стартовый набор тегов, правила приватности и будущие агрегированные сигналы для карточек.

Что считается ошибкой:
Обычному пользователю добавляются новости, stories или публичные авторские подборки.

Нужен ли владелец:
да, подтвердить стартовый набор тегов и можно ли создавать пользовательские теги.

## ROLE-OBJ-001: верх рецензий-рекомендаций в карточке

Зона:
Object Pages.

Ответственный чат:
Object Pages с review от Profile Social и Backend/Auth.

Цель:
Спроектировать, как в карточке объекта, компании или района должен выглядеть блок лучших рецензий-рекомендаций.

Что сейчас не так:
Есть рецензии как социальная идея, но не зафиксировано, какие рецензии попадают наверх и как показывать роль автора.

Можно менять:

- только документацию и UX-сценарий;
- правила сортировки/приоритета;
- copy и статусы для будущего UI.

Нельзя менять:

- object page code;
- `js/pages/object/*`;
- `css/ui-ux-pro-max.css`;
- реальные данные;
- `js/app.js`.

Файлы-кандидаты:

- `docs/ROLE_PROFILES_SCOPE.md`;
- `docs/AUTH_004_BACKEND_AUTH_CONTRACTS_V1.md`;
- будущий отчет Object Pages.

Проверить после:

- рецензия описана как рекомендация, не отзыв/жалоба;
- имя автора может быть скрыто, но контекст виден;
- двойной тег применяется при профессиональной связи с темой;
- публикации компании и партнерские материалы не выглядят независимыми рецензиями.

Ожидаемый результат:
Правила блока `Почему советуют`: приоритеты, роли, двойные теги, статусы актуальности, ограничения для партнерских/компанийских материалов.

Что считается ошибкой:
Рецензии смешаны с отзывами/жалобами или платное продвижение попадает в органический верх как независимое мнение.

Нужен ли владелец:
да, подтвердить формулировку блока и приоритет `лучшие + свежие + подтвержденные`.

## ROLE-BILL-001: тариф физлица `Профиль автора`

Зона:
Billing/Auth + Product / UX Lab.

Ответственный чат:
Billing/Auth.

Цель:
Спроектировать отдельный тариф физлица для ролевого профиля, не смешивая его с B2B-тарифами компаний.

Что сейчас не так:
В проекте есть B2B-тарифы размещения компаний, но нет отдельного тарифа для автора/специалиста.

Можно менять:

- только документацию тарифной модели;
- сравнение с `BILL_001_PRICING_MODEL.md`;
- правила grace/basic/inactive после неоплаты;
- будущие backend fields.

Нельзя менять:

- текущую страницу тарифов компаний;
- billing UI;
- backend/payment код;
- `js/data/company-pricing.js`;
- `js/pages/pricing/business-pricing-page.js`.

Файлы-кандидаты:

- `docs/ROLE_PROFILES_SCOPE.md`;
- `docs/ROLE_PROFILES_OWNER_BRIEF.md`;
- `docs/BILL_001_PRICING_MODEL.md`;
- будущий документ `ROLE_BILL_001_AUTHOR_PROFILE_PRICING.md`.

Проверить после:

- тариф физлица не дает статус компании;
- тариф не покупает статус `Эксперт`;
- тариф не влияет на органический рейтинг;
- после неоплаты профиль не удаляется;
- B2B и физлицо не смешаны.

Ожидаемый результат:
Документ с названием тарифа, ценой-гипотезой, лимитами, форматами, rules after non-payment и списком решений владельца.

Что считается ошибкой:
Тариф автора использует B2B-логику карточек компаний или обещает CRM/заявки/payment до реализации.

Нужен ли владелец:
да, подтвердить название, цену, лимиты, grace/basic/inactive и этап реализации.

Backend/Auth.

Backend/Auth.

Можно менять:

- только документацию;
- будущие API/data candidates;

Нельзя менять:

- backend код;
- mock server;
- frontend adapter;
- реальные auth flows.

Файлы-кандидаты:

- `docs/AUTH_004_BACKEND_AUTH_CONTRACTS_V1.md`;
