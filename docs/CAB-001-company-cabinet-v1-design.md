# CAB-001: v1-сценарий кабинета компании

Дата: 2026-07-06.

Статус: v1 UI реализован отдельным hash-route без backend/auth.

## 1. Цель

`Кабинет компании` в v1 должен показать застройщику или компании, что Kliper.City дает не только публичную карточку, но и рабочее пространство для управления присутствием:

- видеть состояние публичной страницы компании;
- управлять публикациями и stories как будущим контент-каналом;
- видеть объекты компании;
- видеть подписчиков, рецензии и обращения;
- готовить предложения подписчикам;
- понимать базовую статистику и место в репутационном слое.

Кабинет не является профилем пользователя `Мария` и не должен использовать пользовательские сценарии как основу. Это отдельная роль и отдельный контекст.

## 2. Граница v1

Для v1 кабинет входит в продукт, но до backend/auth этапа остается безопасным UI-сценарием без реальной CRM и без настоящих отправок.

В v1 можно проектировать и затем реализовывать:

- отдельный входной маршрут или экран кабинета;
- dashboard компании с локальными или mock-данными;
- список объектов компании;
- визуальный список публикаций;
- визуальное управление stories;
- блок подписчиков;
- блок рецензий;
- блок заявок/диалогов только как входящие обращения без рабочей формы;
- блок предложений подписчикам как заготовку, без реальной рассылки;
- ссылки между кабинетом и публичной страницей застройщика.

В v1 нельзя без отдельного решения владельца:

- добавлять реальную форму заявки;
- делать CRM-воронку;
- отправлять предложения подписчикам;
- добавлять backend/API раньше финального backend/auth этапа;
- смешивать localStorage пользователя и состояние компании;
- править `js/app.js` ради первого прототипа без решения Architect / Main.

## 3. Рекомендуемый v1 route

Главная рекомендация для v1: отдельный SPA-screen или hash-route, не через `#card`.

Предпочтительный кандидат:

```text
#company-cabinet=developerId
```

Пример:

```text
#company-cabinet=brusnika
```

Почему:

- не конфликтует с текущим `#card=...`;
- можно дать прямую ссылку застройщику;
- проще отличать кабинет от публичной страницы;
- можно восстановить состояние после reload.

Альтернативы:

| Вариант | Статус | Комментарий |
|---|---|---|
| `#company-cabinet=developerId` | рекомендуемый v1-кандидат | требует аккуратной интеграции с восстановлением страниц |
| SPA state `companyCabinet` без явного hash | допустимо | меньше URL-ясности, хуже для прямой ссылки |
| Drawer с публичной страницы застройщика | допустимо как быстрый прототип | не ощущается полноценным кабинетом |
| `company-cabinet.html` | запасной вариант | изолирует риск, но выбивается из текущей SPA |
| `#card=...&mode=cabinet` | не рекомендуется | смешивает публичную карточку и приватный кабинет |

## 4. Основной v1-сценарий

1. Пользователь с ролью компании открывает публичную страницу застройщика.
2. В блоке `ДЛЯ БИЗНЕСА / Кабинет компании` появляется CTA входа в кабинет.
3. После входа открывается отдельный экран кабинета конкретной компании.
4. В шапке кабинета видно название компании, статус профиля и ссылку `Публичная страница`.
5. Dashboard показывает краткую статистику, объекты, публикации, stories, рецензии, обращения и предложения.
6. Все действия, которые требуют backend, в v1 помечаются как подготовленные/недоступные до подключения входа и ролей.
7. Возврат из кабинета ведет на публичную страницу той же компании, а не в профиль пользователя.

## 5. Структура экрана

### 5.1 Header кабинета

Содержимое:

- логотип или аватар компании;
- название компании;
- роль текущего пользователя: `owner`, `manager`, `editor` или `viewer`;
- статус профиля: черновик, опубликован, требует проверки;
- ссылка `Публичная страница`;
- действие `Предпросмотр`;
- будущая кнопка `Опубликовать`.

Важно: `Предпросмотр` должен открывать публичный вид компании, а не менять данные кабинета.

### 5.2 Dashboard

Карточки сводки:

- просмотры публичной страницы;
- подписчики;
- рецензии;
- обращения;
- опубликованные объекты;
- stories;
- место в рейтинге категории.

До backend данные могут быть mock/local и должны быть явно отделены от пользовательского localStorage.

### 5.3 Документы и профиль компании

Блок нужен как v1-заготовка, не как юридический документооборот.

Поля:

- реквизиты компании;
- подтверждение застройщика;
- брендовые материалы;
- документы объектов;
- статус проверки.

Граница v1: показывать список и статусы. Загрузка, модерация и юридическая проверка относятся к backend/auth этапу или v2.

### 5.4 Объекты компании

Показывает связанные объекты:

- новостройки;
- готовые ЖК;
- бизнес-помещения, если компания участвует в этой зоне;
- статус карточки объекта;
- ссылка на публичную карточку объекта.

Источник будущей привязки: `developerId` / `companyId`, а не название текстом, чтобы не ломаться при переименованиях.

### 5.5 Публикации

Типы публикаций:

- новость компании;
- ход строительства;
- акция;
- сообщение подписчикам;
- сервисное обновление по объекту.

В v1 это список публикаций и визуальный editor placeholder. Реальный редактор, модерация и публикация требуют отдельного решения.

### 5.6 Stories компании

Сценарии:

- увидеть активные stories компании;
- увидеть черновики;
- открыть предпросмотр;
- подготовить будущую story.

Не смешивать с пользовательскими stories. Stories компании должны быть связаны с `companyId` и публичной страницей застройщика.

### 5.7 Подписчики

Показывает:

- общее число подписчиков;
- новые подписки;
- подписки на конкретные объекты;
- сегменты интереса: новостройки, готовые ЖК, бизнес-помещения.

До backend это только агрегированный/визуальный слой. Нельзя показывать реальные персональные данные без модели доступа.

### 5.8 Рецензии

Показывает:

- новые рецензии;
- рецензии, ожидающие ответа;
- положительные/нейтральные/проблемные отзывы;
- связь рецензии с объектом или публичной страницей компании.

Ответы компании можно проектировать как будущую функцию. В v1 без backend допустим только визуальный placeholder.

### 5.9 Чат, диалоги и заявки

Блок должен называться осторожно: `Обращения` или `Диалоги`, не `CRM`.

В v1:

- список входящих обращений как mock/visual;
- источник обращения: объект, публичная страница, рецензия;
- статус: новое, в работе, закрыто;
- быстрый переход к публичному объекту.

Не делать:

- реальную форму заявки;
- назначение менеджера;
- CRM-воронку;
- отправку сообщений.

### 5.10 Предложения подписчикам

Назначение: показать будущую ценность для компании.

В v1:

- список подготовленных предложений;
- статус: черновик, ожидает backend, архив;
- аудитория: все подписчики, подписчики объекта, интерес к бизнес-помещениям;
- без реальной отправки.

В v2 или после backend/auth:

- сегментация;
- отправка;
- ограничения частоты;
- аналитика доставки;
- история согласий пользователя.

## 6. Роли и вход

Backend/auth запланирован в конце v1, но требования нужно заложить сейчас.

Минимальные роли:

| Роль | Права |
|---|---|
| `company_owner` | полный доступ к кабинету компании, ролям и публикации |
| `company_manager` | обращения, рецензии, предложения, статистика |
| `company_editor` | публикации, stories, черновики |
| `company_viewer` | только просмотр dashboard |
| `kliper_admin` | модерация, подтверждение компании, поддержка |

Правила:

- один пользователь может иметь обычный профиль и роль компании, но интерфейсы должны быть разделены;
- кабинет открывается только в контексте `companyId`;
- пользовательский профиль `Мария` не является fallback для кабинета компании;
- localStorage-ключи компании должны иметь отдельный namespace, например `kliper.companyCabinet.*`;
- после backend/auth localStorage должен стать только временным UI cache, а не источником прав.

## 7. Связь с публичной страницей застройщика

Публичная страница и кабинет связаны, но не являются одним экраном.

Из публичной страницы:

- CTA `Кабинет компании`;
- переход в кабинет только для роли компании или как демо-CTA до auth;
- публичная статистика не должна показывать приватные данные.

Из кабинета:

- ссылка `Публичная страница`;
- предпросмотр публичного вида;
- быстрые ссылки на объекты;
- рецензии и stories должны вести к соответствующим публичным поверхностям.

Запрещенный сценарий: открывать кабинет через `#card` и подменять содержимое публичной карточки.

Рискованные файлы:

| Файл | Почему риск |
|---|---|
| `js/app.js` | legacy/generated SPA-каркас, не редактировать без решения |
| `index.html` | подключение новых модулей влияет на весь сайт |
| `js/behavior/page-restore.js` | может конфликтовать с hash-route |
| `js/pages/object/*` | зона публичных страниц объектов/застройщиков |
| `js/behavior/user-page-finalizer.js` | зона профиля пользователя, не смешивать с компанией |

## 10. V2 backlog

Кандидаты v2 или post-auth этапа:

- полноценная CRM-воронка;
- реальные заявки и формы;
- отправка предложений подписчикам;
- сегментация подписчиков;
- управление ролями сотрудников компании;
- модерация документов;
- аудит действий;
- API кабинета;
- аналитика публикаций и stories;
- история коммуникаций;
- ограничения частоты рассылок;
- интеграции с внешними CRM;
- billing/тарифы для компаний;
- кабинет для управляющих компаний, если продукт выйдет за рамки застройщиков.

## 11. Вопросы владельцу

1. Какой формат выбрать первым: отдельный экран, drawer с публичной страницы или отдельный HTML?
2. Какой route закрепляем для v1: `#company-cabinet=developerId` или другой?
3. Кто первый пользователь кабинета: застройщик, менеджер отдела продаж, маркетолог или админ Kliper?
4. Какие блоки должны быть кликабельными в v1, а какие только визуальными?
5. Нужен ли раздел `Документы` уже в первом UI-прототипе или только как backlog?
6. Как называть блок входящих: `Обращения`, `Диалоги`, `Заявки` или иначе?
7. Должны ли предложения подписчикам быть видны в v1 как черновики?
8. Нужно ли показывать кабинет обычному пользователю как демо `Для бизнеса`?
9. Должен ли кабинет покрывать только застройщиков или также компании из бизнес-помещений?
10. Какие данные можно mock-ать до backend/auth, чтобы не создать ложное ощущение рабочей CRM?

## 12. Следующий безопасный шаг

После решения владельца по route и формату можно ставить отдельную задачу CAB-002:

- создать UI-прототип кабинета без backend;
- не трогать `js/app.js`, если можно подключить отдельный модуль;
- не менять профиль пользователя `Мария`;
- не добавлять реальную форму заявки;
- проверить desktop/mobile/dark/public developer page после реализации.
